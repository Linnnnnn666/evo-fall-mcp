> 目的是留下"这套系统不只跑得动，还能被维护和验证"的工程记录。

## 二、清理与升级动作

### 清理原则（保留什么、删什么）

| 类别 | 处理 | 理由 |
|---|---|---|
| 第三方市场插件（4 个） | **删除** | 来源分散、非自研、统一标准模式 |
| 实验性路由预设（Router Standard） | **删除** | 标准化 agent 行为 |
| **自研进化产物（插件）** | **保留** | 这是双层自进化的运行时证据 |
| 插件需求文件 / 隔离区 | **保留** | 进化审计链的一部分 |

### 关键：删插件必须同时改三处，否则 DSH 起不来

```
1. <profile>/package.json   → dependencies 与 dsh.profile.bundles 都要删
2. <profile>/cordis.patch.yml → 对应的 insert / 插件挂载条目要删
3. <profile>/node_modules/    → 插件实体目录要删
```

> 只删 node_modules 而不改 `bundles`，DSH 启动时会因为找不到 bundle 直接失败。

### 升级前后

| 项 | 前 | 后 |
|---|---|---|
| DSH 版本 | 0.1.0-rc.7 | **0.1.5-rc.3** |
| DSH-1 profile（headless） | 4 个第三方插件 + 路由预设 | **标准模式 + 4 个自研进化产物** |
| DSH-2 profile（headless-builder） | 1 个第三方插件 + 路由预设 | **标准模式（干净隔离环境）** |

## 四、自进化闭环实录（**本次的核心验证**）

### 投放的需求

| 项 | 内容 |
|---|---|
| 能力 | LD6002B 毫米波雷达 TinyFrame 帧解析与校验（校验 SOF/长度/双校验和，payload 解码为 float32 点云） |
| 工具名 | `parse_ld6002b_frame` |
| 选它的原因 | **真实痛点**（雷达 UART 丢字节导致帧错位，需要调试工具）+ 纯计算（符合插件安全约束） |

### 时间线（总耗时约 200 秒）

| 阶段 | 耗时 | 证据 |
|---|---|---|
| 轮询器拾取（10 秒周期） | <10s | 需求状态 `pending → processing`；进化日志写 `plugin_req_started` |
| **DSH-2 隔离构建** | ~110s | 插件落盘 `plugins/ld6002b-frame.mjs`（18.6 KB）；`source: self-made`（市场搜索无果后自制） |
| 安装（备份 + 锁 + 原子写 + YAML 校验） | ~180s | patch insert 数 3 → 4；自动生成 patch 备份 |
| DSH-2 自验证 | ~200s | 正例 / 反例 + 离线协议向量与边界用例 |
| 需求闭环 | 完成 | 需求文件回填 installed_plugin / installed_tools / source / verification |

### 独立验证（不依赖系统自检）

除了系统自检，另做了一轮**独立验证**：

| 检查 | 结果 |
|---|---|
| 插件文件体检 | `node --check` 通过；危险模式扫描为空；零第三方依赖 |
| **离线单元测试 4 用例**（直接加载插件调用工具，不经 LLM） | ① 合法帧 → `valid=true`，float32 解码正确 ② 篡改校验和 → `valid=false` 并给出 got/calc 差异 ③ 非 SOF 开头 → **能识别前导噪声并报告 SOF 首次出现的偏移** ④ 带 `0x` 前缀与空格 → 正常解析 |
| DSH-1 真实会话调用 | 工具可用；坏帧被正确识别并解释失败原因 |
| 隔离区 | 空（本次进化无失败插件） |

> 结论：**双层自进化在新版本下端到端可用**，产物质量达到生产可用水平。

## 五、遗留问题（如实记录）

### 1. 插件注册表未落盘 → 去重检查失效

| 项 | 内容 |
|---|---|
| 现象 | 运行目录下的 `plugins.json` 从未生成 |
| 根因 | 保存函数 `_save_plugins()` 有实现，但代码中**没有任何调用点**；加载函数在文件缺失时返回空表 |
| 影响 | 需求进入时的"已有同能力工具"去重检查永远命中不了 → **同一工具名重复投递会被重复构建**，而不是被标记 `skipped` |
| 修复方向 | 在插件构建成功分支补一次注册表写入 |

### 2. 插件安装成功缺少审计事件

| 项 | 内容 |
|---|---|
| 现象 | 进化日志里只有 `plugin_req_started` / `rejected` / `skipped` / `scan_warn`，**没有"安装成功"这一条** |
| 影响 | 安装结果只落在需求文件里，审计日志不完整 |
| 修复方向 | 成功分支补一个 `plugin_installed` 事件（含插件名、工具列表、来源） |

### 3. 历史需求文件指向已清理的市场插件

两条历史需求（二维码、哈希）当时的来源是**市场安装**（第三方插件），
本次按"统一标准模式"清理后，这两个需求文件里的 `installed_plugin` 指向已不存在的插件。
功能不受影响（对应能力在本仓库 `dynamic_tools/` 里有自研实现），仅造成叙事层面的不一致。

## 六、可复用的经验

1. **删插件是"三处联动"**：`package.json`（依赖 + bundles）、`cordis.patch.yml`（挂载）、
   `node_modules`（实体）。只删一处必炸。
2. **升级前先备份，且备份要包含"被删除的东西"**：本次备份包含两个 profile 配置、
   设置文件、路由预设、全部进化产物与需求文件，可完整回滚。
3. **系统自检不能替代独立验证**：自身验证跑在受测同一套机制上，必须用外部手段
   （离线单测 / 产物核验）再确认一次。
4. **升级后要验证"兼容性"而不只是"能启动"**：检查代码里对已删组件的引用、插件安装格式、
   健康检查流程是否仍然工作。
5. **审计缺口要如实记录**：本次发现的两个缺口（注册表未落盘、安装事件缺失）不影响
   功能，但影响"可审计"的可信度——写进文档比藏着更有价值。
